# CodexをHoverPocketの共通コントローラーにする設計

状態: 2026-09-07に実装を承認。macOSの接続と隔離検証を実装し、追加の音声確認設定・天気とともにbuild638へ本番反映済み。物理マイクの総合受入は未完了。具体的な接続契約は [共通コントローラー契約](20260907_CODEX_APP_OS_CONTRACT.md)。
既存基盤: [個人用ツール基盤](20260906_POCKET_TOOLS_PLATFORM.md)。この文書は音声・画面・ツール開発を接続する設計の正本。

## 目的と維持する体験

話しかけるだけで、必要な画面を見ながら既存機能の操作、新規ツールの作成、改善・批評、不要な追加ツールの整理ができる。ユーザーは現在の音声操作に満足しているため、その接続方式、応答性、既存tool、承認・実行readbackを維持する。

音声接続、生成作業、Hostの実行処理を分離する。ユーザーからは一人のCodexと話している体験にする。音声側も既存操作の判断・実行依頼を担当し、生成workerを全操作の中継にしない。

## 役割

| 担当 | 責務 |
|---|---|
| 音声側Codex | 対話、対象特定、画面選択、既存操作、生成・修正依頼、進捗と結果の説明、音声での確認 |
| 生成側Codex Astra | 別セッションで仕様ガイドを参照し、ツール定義・UI・データ項目を生成・修正。検証結果を使って改善 |
| HoverPocket Host | 機能一覧・画面状態・生成jobの管理、検証、導入・削除・復元、保存、権限、標準機能保護、実行後readback |

生成側は既存CodexAppServerPocketGeneratorを再利用。モデルはGPT-6 Astra、推論の既定はMedium、変更済みの選択を保持する。生成要求ごとに別のephemeral threadを使用する既存方式を土台とする。音声のモデル・transportを生成側に合わせて置換しない。

生成workerが保存データ、標準アプリ本体、認証情報を直接変更する構成にはしない。導入や管理は生成workerの自由なコード実行ではなくHostの既存処理が担う。

## 代表的なbefore / after

- 現在: 音声で今日の予定を読み上げられるが、該当画面を開く操作はつながっていない。
- 更新後: 今日のカレンダーを開き、表示した日付・予定と一致する内容を説明する。「その次」で同じ予定一覧から対象を選べる。
- 現在: 設定画面から生成を依頼し、利用者がプレビュー・導入を操作する。
- 更新後: 音声が生成jobを起動してすぐ対話へ戻る。Hostがjobの進行を保持し、検証後にパネルへ試作を表示する。音声確認後にHostがその版を導入してreadbackする。

## 共通の機能一覧と操作

- Hostが標準providerと導入済み追加ツールを一覧化し、安定したID、用途、利用可能操作、表示先、利用可否を音声側へ返す。
- 追加ツールの定義・保存項目・許可された操作をHostから発見できるようにし、ツールごとに音声用の個別実装を増やし続ける構成を避ける。
- 標準機能と追加機能は別管理。将来の公式アップデートで増える標準機能も、Host管理の分類で削除・生成による置換を拒否する。生成物が自身の所有区分を宣言して保護を回避できないこと。
- 設定画面と音声操作は同じサービスを呼ぶ。標準機能の表示・非表示は削除と分ける。
- 自作ツールの登録を増やしても、音声セッションの機能一覧が更新されないままにならないよう、導入・更新・削除後に音声側の一覧も同期する。

## 画面と会話の状態

- 現在のprovider、表示日付、選択中の予定・レコードなどをHostが一元管理する。画面内のStateと音声用の値を別々の正本にしない。
- 画面操作の要求はprovider IDと意味のある選択対象で表し、座標クリックへ変換しない。外部IDを音声へ無制限に渡さず、既存の対象特定・revision検証を使う。
- 会話中は関連画面を自動表示する。取得中・取得失敗・画面表示失敗を区別し、未表示や未取得なのに成功と説明しない。
- パネルを閉じても会話を続ける既存設定を尊重する。画面を開く操作はマイクの開始・ミュート解除を意味しない。ユーザーが編集中の内容を画面切替で破棄しない。

## 生成jobと音声確認

- 音声toolの呼出しを生成完了まで長時間待たせず、Hostはjob IDと受付状態を返す。
- 一度に実行する生成jobは既存controllerの制約に合わせて1件。重複要求を二重起動せず、取消・失敗・完了を区別する。
- 生成中も予定確認などの既存操作を続けられる。完了・失敗は同じjobの状態から会話と画面へ伝える。会話の切断やパネルの閉鎖を、未確認の導入承認として扱わない。
- ユーザー採用方針: 試作・検証は自動。2026-09-07の追加依頼により、通常操作と削除操作の確認を個別設定する。確認ONの場合は追加・更新・削除の直前に音声で確認し、OFFならHostが直接実行する。「それで追加」「やめて」を、対象job・ツール・版・変更内容に結び付ける。確認後に内容が変わった場合は前の確認を使わない。
- 自作ツールはデータ保持のアンインストールを基本とし、記録・履歴を含む完全削除は別操作として明示する。既存Host管理処理を再利用する。
- 切断後の進行再開や通知を無条件に追加しない。既存checkpointで残せる状態を利用し、新規job永続化の要否・形式は実装前に確定する。

## 生成品質

既存の寸法・共通テーマ・collection保存・workflowガイドと契約検証を維持する。契約検証を「操作できる」「見た目が最適」と同義にしない。

実previewで、描画・スクリプトエラー、最小パネルと最大文字、overflow、主要な入力・保存・検索、取消を確認する検証を追加する。実ユーザーデータに対してテスト操作を行わず隔離した試用データを使う。結果は生成workerへ戻し、回数を限定して修正する。検証できない機能を成功扱いせず利用者へ提示する。

## 声の選択

設定の音声カテゴリから利用可能な対話音声を選択・保存できるようにする。候補は実際の接続先が対応する一覧を確認する。接続中に変えられるか、次回接続からかを明示し、声の変更を理由に会話履歴を無断で失わない。保存形式と切替タイミングは実装時の対応API確認を経て確定する。

## 正本・互換性・ロールバック

- ツール定義、collectionデータ、履歴・導入receiptは既存ストアを正本とする。音声用コピーを新たな保存データの正本にしない。
- 画面選択は原則セッション内状態。job ID・ツールID・版・承認対象を区別する。日付は利用者のタイムゾーンで解釈し、時刻の外部形式は既存契約に従う。
- 新しい音声tool/状態通知/設定保存の具体的なschema、代表fixture、利用側への影響は実装前の契約設計として確定する。本書をそのschemaが実装済みという根拠にしない。
- 当面の接続追加にツール定義v2やレコード形式の移行は求めない。必要になった場合は移行・復元の設計と検証を同時に行う。
- 接続追加を戻した場合も、既存の音声操作、設定からの生成・管理、導入済みツールと記録を保持する。
- macOSを先行する。Windowsに同等機能があるとは扱わず、別受入とする。本番配信は別途実施する。

## 実装順と受入条件

1. Host共通の機能一覧と画面操作を追加。音声会話を続けながら今日のカレンダーを表示し、内容一致・取得失敗・手動選択との同期を実音声で確認。
2. 既存生成controllerをjobとして音声へ接続。生成中の別の質問、取消、プレビュー、対象を指定した音声承認、導入readbackを確認。
3. 追加ツールの項目操作、修正・批評、削除・復元を接続。標準機能の削除拒否、データ保持、同名の対象、古い版への誤承認を検証。
4. 実previewの検証と修正ループを追加し、複数種類の実モデル生成で受入。声の選択・保存・反映も実音声で確認。

全段階で既存の音声tool契約、承認、タイマー・付箋・予定等の回帰検証を実施する。音声入口だけのテストや固定fixtureだけで全体を完了扱いにしない。
