# HoverPocketのリキッドアニメーション

設計: Claude Opus 5.5（このMacのClaude Code、推論high、会話 `fe82e2a8-b3e8-47e8-9826-45f08052d343`）。実装: Codex。ユーザー指定の元動画と抽出フレームを渡し、Claudeは60fpsの輝度解析も実施した。

10月2日の接合部の再調整は、Claudeの利用枠上限で新しい設計確認が実行できなかったため、既存の凹曲線設計を基にCodexが実装・検証した。新しいClaudeレビューと実物のノッチでの見た目の受入は未実施。[今回の検証記録](../../progress/2026-10/2026-10-02_hover-pocket-liquid-junction.md)。

## 動画から採用した動き

ノッチ幅の黒い面が上端から広がり、中身が後から現れる。閉じる時は中身が先に消え、面が起点へ戻る。Claudeの計測では約180〜200msで減速し、行き過ぎは観測されなかった。編集のズームが含まれるため時間は目安。ぼかしがアプリ由来か編集由来かは未確定。

## Macの実装

- ウィンドウは開閉中に最終寸法へ固定。入口とパネルの`animationBehavior`を`.none`にし、OS標準の表示・退避時の伸縮を重ねない。AppKitの塗り・マスク・縁線へ同じ輪郭を渡す。SwiftUI、WebView、カメラを載せるコンテナを切り抜く。
- 開き具合`p=0...1`から輪郭を導出する。第一案はノッチ下で幅を`1-(1-p)^1.8`、本文高さを`p^1.3`で伸ばす。実ノッチの上半分は描画せず、下端最大6ptの接合部だけを同じ進捗で変形させる。第二案はノッチの幅・高さ・底の丸みを持つ形から、同じ`p`で幅と下端を同時に伸ばす。動きの緩急はばねが担う。
- 第一案の本文の起点幅はノッチ幅（会話中は108pt追加）。接合部の隠れた起点は実ノッチの左右を2ptずつ内側へ入れる。ノッチなしの首は会話開始・終了で動かない168pt固定とする。第二案の起点幅にはノッチ幅の左右に1物理ピクセルを足す。
- 中身は拡大縮小せずフェードで追従。透明度は`smoothstep(.38,.88,p)`。第一案は最大10pt移動し、第二案は上端バーが滑らないよう移動を行わない。
- 臨界減衰ばねのresponseは開く0.24秒、閉じる0.20秒、リサイズ0.28秒。位置と速度を引き継いで目標だけを切り替える。
- 閉じ始めの待ち時間は60ms。閉じる進捗が0.012以下で隠す。描画コールバック停止時の保険は450ms。
- macOS 14以降のdisplay linkを動作中だけ使用。停止時にはinvalidateする。既存のホバー監視タイマーは継続するため、アプリ全体のCPUゼロは主張しない。
- サイズ・音声レーン変更では旧・新位置を含むウィンドウを確保し、面の矩形をばねで補間。終了後に新寸法へ確定する。
- 表示内容は選択先だけを140msで表示。選択中の背景は1枚をばねで移動。ボタンのホバー・押下は100ms。
- 「視差効果を減らす」有効時は面の変形を省き、120ms/90msのフェード。サイズ変更と選択背景は即時。検証時の即時モードは従来どおり。
- 不可視の中身はクリックとアクセシビリティの対象外。開閉中の世代を照合し、古い完了処理を適用しない。外部ドラッグ後は進捗をゼロへ戻す。

## 設計からの実装上の調整

既存の`Views/PocketSurfaceView.swift`と衝突するため新規クラスは`LiquidPanel`で命名。ばねは数値積分の代わりに臨界減衰の解析解を使用し、60Hz/120Hzで同じ軌道にした。Viewのbacking layerの反転はAppKitへ任せ、塗り・内容コンテナ・縁線を同じ反転座標で扱う。レイヤーの透明度はAppKitの再同期で変わらないよう色へ含め、apply時にマスクと色を再設定する。

## 検証

`--verify-liquid-motion`は実パネルで両案×4サイズ、接続済み画面、開いたままの切り替え10回、途中反転30回、外部ドラッグ後の再表示、復帰、描画更新停止、100回開閉を確認する。両案で5点各600msの静止ホバー、離脱20ms後の再進入による予約取消、離脱による自動閉鎖も検査する。明示的に開いた時の保持を解除し、実運用と同じ閉じる判定へ検査位置だけを渡す。パネルのPNGはAppKitのViewキャッシュ描画。両案の実WKWebView fixtureで可視部分・隠れた内容・メニュー帯のクリック判定も検査する。これとは別に、ScreenCaptureKitで自分のWKWebViewテストウィンドウを撮り、面の外に内容が漏れないことを画素で検査する。画面収録許可がなければ画素検査だけskipする。`--verify-panel-layout`も使う。

Windowsは設計のみで、今回のコード変更・受入の対象に含めていない。WPFでは固定ウィンドウ、同じばねと輪郭、WebView2のスナップショットを伸縮なしで使う。実装・CI・実機検証は別途必要。

公式仕様: [画面に同期したNSViewのdisplay link](https://developer.apple.com/documentation/appkit/nsview/displaylink(target:selector:))、[CALayerの座標反転](https://developer.apple.com/documentation/quartzcore/calayer/isgeometryflipped)。

## ノッチとの接続と2種類の表示

[第一案の参照画像](../../output/liquid-motion-2026-10-01/accepted-preserve-menu.png)を基に、左右のメニューバーを残し、ノッチの下端とパネルの接合部だけを液体の表面張力の凹曲線でつなぐ。10月2日の写真で、全ノッチ帯を無描画にした結果、接合部が平らになって分離して見えることが指摘されたため、この条件を改めた。上半分と下端最大6ptの接合帯以外は引き続き描画しない。接合部に常時の矩形を置かず、閉じた時の面積と丸みを0にする。本文の縁線も接合面より上を切り、中央の横線を作らない。

[第二案の確定画像](../../output/liquid-motion-2026-10-01/accepted-cover-menu.png)はパネル幅の範囲で画面上端まで覆う。上端の左右は、画面端へ外側に広がる凹曲線でつながる。中央の物理ノッチ幅に左右8ptの余白を足した領域へ内容を置かない。左右には実タイマーの残り時間（未使用時は選択中の機能）と実音声状態を表示し、会話中にはミュートと終了を操作できる。

設定は「表示と操作」→「パネル」→「ノッチとパネルの接続」。`PanelAttachmentStyle`の`preserveMenu`（既定）と`coverMenu`をUserDefaultsの`panelAttachmentStyle`へ保存。未設定・未知の値は第一案。開いたまま変更すると、開閉とは別の0.28秒responseのばねで輪郭を連続変形する。Reduce Motionでは即時変更。 同じ欄の`automaticallyCoverMenuOnNoNotchDisplays`は既定falseでUserDefaultsへ保存する。オンでは表示先の`attachmentMetrics.notchWidth == 0`の場合だけ第二案へ切り替える。保存済みの手動選択は書き換えず、ノッチがある画面ではそれを使う。`HoverMenuStore.effectivePanelAttachmentStyle`を背景と上部バーの共通の判定として使い、設定変更は既存のリサイズ経路で再解決する。[ノッチなし画面の追加変更と検証](../../progress/2026-10/2026-10-02_hover-pocket-no-notch-attachment.md)。

第二案は`幅=N+(本文幅-N)*p`、`下端=H+本文高さ*p`とし、`p=0`からノッチの幅N・高さHを持つ。底の丸みは10ptから18pt、上端の凹曲線は0ptから8ptへ連続して変わる。本文矩形の上端は`min(H,下端/2)`とし、底の角丸と上の角丸の合計が本文矩形の高さを超えないよう制限する。最終的に本文の位置・寸法は既存のまま。第二案の動きはユーザーが承認しており、維持する。

第一案の実ノッチの接合量は`g=smoothstep(0,.4,p)`。最大接合位置`T`は`H−min(6,H/2)`を画素の端へ切り上げ、描画上端を`H+(T−H)*g`とする。隠れた起点幅は実ノッチ幅−4pt。凹曲線の丸みは`min(6*g,左右の広がり/2,H−描画上端)`で、垂直の矩形が残らない。Bezierの既存の接線を使って垂直から水平へ滑らかにつなぐ。塗り・内容マスク・クリック判定は同じパスとし、本文の縁線は接合部を横切らない。`p=0`は描画上端H・本文高さ0・丸み0で面積0。ノッチなしでは首の幅と下段の接合曲線を維持し、描画上端を0にして両側を直線で画面上端まで延ばす。第一案の上端の丸みは0。案の切替途中は各寸法を補間し、角が折り返さないよう制限する。ノッチ機の塗りは不透明、ノッチなし画面は既存の塗りのフェードを残す。閉じる判定は開いた画面の論理的な入口と実際の輪郭の和集合で、どちらも4ptの許容幅を使う。クリック判定は実際の輪郭だけを使う。

4サイズの既存本文サイズは維持し、画面ごとのNSScreen.safeAreaInsets.topから求めるヘッダー高さを上へ追加する。ノッチなし画面はメニューバーの高さと168ptの首を使い、第一案の首は上端まで直線でつなぐ。第二案の中央には無表示領域を作らない。両案のウィンドウは同じ寸法で、左右8ptの透明な余白が上端の凹曲線を収める。パネルの上端は画面端へ一致させ、隣接した画面へはみ出さない。

塗り・内容マスクは同じ1本の輪郭。塗りは純黒、首と上端に縁線を置かず、ウィンドウの影は無効にする。開いている間は同じ画面の入口ウィンドウを隠し、閉じると再表示する。第一案の透明領域でメニュー操作を奪わないよう、形の内外でignoresMouseEventsを変更する。マウスの移動・ドラッグ監視は開き始めから行い、閉じると解除。描画更新は静止時に停止する。既存の常駐ホバー監視は残る。

Apple公式仕様: [ノッチ左の表示可能領域](https://developer.apple.com/documentation/appkit/nsscreen/auxiliarytopleftarea-uglc)、[statusBarのウィンドウレベル](https://developer.apple.com/documentation/appkit/nswindow/level-swift.struct/statusbar)。パネルはstatusBar+1、ポップアップメニューより下へ置く。外部画面、表示倍率変更、フルスクリーンの実機受入は各環境で確認する。

追加録画で、数式の上端が固定でも、OS標準のウィンドウ表示によって面全体が一時的に下がり、上に白い隙間が出ることが判明した。Appleの[animationBehavior](https://developer.apple.com/documentation/appkit/nswindow/animationbehavior-swift.property)の仕様に沿って標準の伸縮を無効にする。回帰検証では独立windowの撮影に加え、実ディスプレイのパネル領域を連続撮影する。第二案で検証内だけ`.default`を戻す対照を設ける。製品経路では第二案の上端の隙間0・ノッチ形の起点・幅と深さの同時成長、第一案の接合帯以外の描画画素0・接合の成長・ノッチ下端をまたぐ隙間と横線の画素0を確認する。撮影検査だけ起点を60ms保持し、確実に初期形状を記録する。対照の閉じる処理は`.none`へ戻してから行う。対照に変位が出ない環境は検出力を未確認として記録し、製品の不具合と区別する。画面収録権限を要求せず、未許可の環境では撮影だけskipする。
