# 素材ライブラリの端末間同期 要件案

## 1. 今回の依頼と決定の範囲

ユーザーの依頼は、公開済みWindows 0.2.10と同等のライブラリをMacへ実装することと、Windows・Mac、将来はiPhoneで「完全同期」するための要件整理である。Macのローカル機能は別タスクで実装する。本書は同期の要件案であり、同期コード、データ移行、クラウド契約、Eagle/Syncthingの設定変更を承認するものではない。

今回明示された要件は、WindowsとMacの双方向同期、将来のiPhone対応、既存の自作Eagle同期に近い利用体験、実装前の要件整理。以下の同期方式・競合処理・性能目標は、その目的を満たす提案であり、ユーザーが個別に承認済みの仕様や実測結果ではない。

ローカルライブラリの正本は[素材ライブラリ初期版](asset-library-v1.md)、既存のID・原本・バックアップ形式の正本は[共通契約](../../shared/asset-library/README.md)。本書は後続の同期機能を定め、既存機能のアカウント不要・オフライン利用を維持する。同期は明示的に有効にした利用者だけが使う。

## 2. 「完全同期」の意味

接続が回復し、転送・検証・適用が終われば、参加端末から同じ素材と整理結果を利用できる。ファイルの追加だけでなく名前変更、分類変更、ごみ箱への移動と復元も双方向に反映する。切断中の即時一致は求めず、未反映の状態と対象端末を利用者に示す。

| 対象 | 同期する内容 |
| --- | --- |
| 原本 | 写真、動画、PDF、その他の通常ファイルの全バイト。元の品質・形式・SHA-256を維持する |
| 素材情報 | 安定したID、表示名、拡張子、種類、取り込み日時、サイズ、原本ハッシュ、お気に入り、由来フラグ |
| 分類 | フォルダ・タグのIDと名前、フォルダ階層、所属、空フォルダ |
| 保存検索 | スマートフォルダの名前と検索条件。検索条件v1/v2の意味を維持する |
| 編集結果 | 画像編集やスクショ装飾で確定した画像。現行版は注釈を画素へ統合した別素材として保存するため、その原本と分類を同期する |
| ごみ箱 | ごみ箱へ移動した状態、復元、削除履歴。端末のOSごみ箱の内容は対象外 |

編集中で未保存の図形や収録途中のファイルは確定後に同期する。編集レイヤー・動画編集・OCR・Eagleとの常時相互同期は追加要件とし、現行ライブラリに存在しない機能を今回の前提にしない。

端末ごとに残すものは、ウィンドウ位置、表示倍率、選択・スクロール位置、ショートカット、撮影通知秒数、撮影先モニター、マイク、OS権限、キャッシュ、作業コピー、資格情報、同期の端末ID。クリップボード履歴も自動同期の対象にせず、明示的にライブラリへ保存した素材だけを同期する。外部ファイルの絶対パスや取得URLは既存のバックアップ契約どおり送らない。

WindowsとMacは、全原本を両方へ保持する方式を既定の提案とする。iPhoneは全件の一覧・分類を共有し、原本は必要時に取得し「端末に保存」で固定できる方式を推奨する。全原本を常時持つ選択肢も設けるかは容量と利用方法を確認して決める。原本未取得のiPhoneを「原本の取得完了」と表示しない。

## 4. 推奨する構成

各端末のローカルライブラリを保ちながら、認証した同期用サービスを経由して原本と変更履歴を受け渡す構成を推奨する。理由は、送信元のPCを終了した後でも、保存済みの変更を別のPCやiPhoneから取得できるため。WindowsとMacを同時に起動する必要をなくすことを目標にする。保存先の事業者や費用は未決定で、既存のクラウドサービスの契約・公開設定を変更しない。

同期の流れは「この端末へ保存 → サービスへ転送・検証 → 相手へ転送・検証 → 相手のライブラリへ適用 → 適用結果を確認」。大きい動画を転送していても、名前変更や小さい素材の反映を止めない。

代替案は、現在のEagleに近い端末間転送方式。クラウドの保管費を抑えられる一方、受け渡し可能な端末や常設機の稼働に依存する。iPhoneからの取得経路、常設機の管理、PC停止中の挙動を別途設計する必要がある。方式はユーザーへ確認中で、回答前にいずれかを実装しない。

SQLiteのDBファイルや開いたライブラリフォルダを、そのまま双方から上書きする方法は採らない。SQLiteは書き込み中の単純コピーで不整合が起き得るため、各端末のDBへ検証済みの変更を適用する。バックアップには既存方針どおり整合したスナップショットを使う。[SQLite公式の説明](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)

## 5. 操作・整合性の要件

| ID | 必須動作 | 受入条件 |
| --- | --- | --- |
| SY-01 | 同期を有効にしたライブラリへ端末を登録する | 所有者の確認なしで別端末が参加できない。登録時に既存素材の件数・容量・重複候補を示す。空の端末をつないで他端末の素材を消さない |
| SY-02 | WindowsとMacの追加・変更を両方向へ反映する | 原本のハッシュ、対象メタデータ、分類、検索条件が双方で一致する。対応外形式も元のバイト列で保持する |
| SY-03 | オフラインで追加・名前変更・分類・編集・ごみ箱・復元を行える | 再接続時に未送信分を再開し、アプリ再起動でも操作を失わない。保存直後に送信不能でもローカル保存は成功として扱う |
| SY-04 | 重複した要求と、順序が前後したイベントを安全に扱う | 同じ変更を複数回受け取っても一度だけ適用する。親フォルダや原本の到着前は待機し、再試行で完了する |
| SY-05 | 同一内容を別端末で同時取り込みしても収束する | 同一SHA-256は通常・ごみ箱を通して一つの素材という現行契約を維持。分類を失わず統合し、表示名・お気に入り・ごみ箱状態の相違は競合として扱う |
| SY-06 | 同名の別内容は両方残す | 表示名だけで上書き・同一視しない。ファイル名のOS制約があってもUUIDで原本を保存する |
| SY-07 | ごみ箱への移動・復元も同期する | Deleteで恒久削除しない。復元後は元のID・原本・分類を保持。他端末の削除と同時の編集を黙って破棄しない |
| SY-08 | 大きなファイルの中断と容量不足から復旧する | 分割転送の再開、最終SHA-256検証、必要容量の表示がある。キャンセルや失敗でも確定済み原本を消さない。サービス上限を超える動画を部分成功にしない |
| SY-09 | 同期状態を端末別に示す | この端末に保存済み、転送待ち、転送中、反映待ち、同期済み、オフライン、競合、失敗を区別する。再試行・一時停止・最終成功時刻・未反映件数を確認できる |
| SY-10 | 手動再同期と修復を行える | 再送は重複を増やさず、欠損や変更された原本を検知する。必要な原本を他の検証済みコピーから回収できない場合は失敗を示す |
| SY-11 | 端末を解除しても残すデータを明示する | 「この端末のキャッシュ解放」「この端末の同期解除」「全端末の素材をごみ箱へ移す」を区別する。解除は他端末の削除にならない |
| SY-12 | 同期とバックアップを別に扱う | 端末間で同期した誤操作からも復元できる独立バックアップを残す。空ライブラリへの既存バックアップ復元を壊さない |

### 同期済みの判定

送信要求の成功や転送ツールの未転送数0だけでは同期済みにしない。合意した変更の版、素材・分類・検索の正規化した内容、原本のハッシュ、未適用・競合・失敗の有無を確認する。全原本保持の端末では全原本の検証まで、必要時取得の端末ではメタデータと取得予定の状態までを別々に示す。ネットワークから見えない端末は「反映待ち」とし、全端末完了を推測しない。

## 6. 同時変更・削除・重複の扱い

推奨する原則は「異なる項目の変更は合流し、同じ項目の衝突は両方を保護する」。競合処理のUIには両端末の内容と変更元を出し、「こちらを使う」「相手を使う」「両方残す」の適用可能な選択肢を示す。解決そのものも一つの変更として同期し、解決前の版を追跡する。

| 同時操作 | 期待する結果 |
| --- | --- |
| Windowsで名前変更、Macでタグ追加 | 両方を反映 |
| 同じタグを両端末で追加 | 一つの所属へ統合 |
| 同じタグの追加と解除が同時 | 観測していない追加を解除しない方針を契約化し、両OSで同じ結果にする |
| 同じ素材名を別々の名前へ変更 | 両方の候補を保持して競合表示。端末の時計だけで片方を消さない |
| 同じ親に同じ正規化名の分類を作成 | 一つの分類へ収束し、全所属を保持。親移動や階層循環が絡む場合は競合へ退避 |
| 画像を両端末で編集して保存 | 現行の別素材保存に沿い、双方の編集結果と原本を残す。同じ結果の重複はSY-05に従う |
| 一方でごみ箱、他方で編集・復元・分類変更 | 自動で恒久削除せず、双方の変更を保護して競合表示 |
| オフライン端末が古い素材を再送 | 削除の履歴を参照し、削除済み素材を勝手に復活させない |
| 既存の同一原本を片方ではごみ箱に保持 | 重複統合だけで復元しない。状態の相違を確認できるようにする |

既存の各素材IDを通常の同期や名前変更で変えない。ただし別端末で独立作成した同一SHA-256のIDが二つある場合は、決定的な代表IDと旧IDの対応を保持する必要がある。参照と未適用イベントを失わず一意制約を満たす方法を、実装前に共通契約とfixtureで固定する。DB版1のまま対応できると断定しない。

通常の削除はごみ箱へ移すだけとし、自動の恒久削除は既定で行わない。将来「完全に削除」を提供する場合は、全端末に影響する旨と復旧可能期間を表示する。原本を実際に回収する条件は、保持期間、全参加端末の適用確認、競合なし、参照なし、バックアップ方針を満たすこと。削除履歴は古い端末の復帰で復活を起こさないよう保持し、履歴を短縮した後の古い端末には再照合を要求する。長期不在端末は利用者が明示解除できる。

## 7. 互換性・保護・復旧

同期データにはライブラリID、端末ID、素材/分類/検索ID、変更ID、変更元の版、プロトコル版、原本ハッシュとサイズを持たせる。日時はUTC、サイズはバイト、Unicode正規化と保存検索の意味は共通契約を使う。低水準の形式は実装前の設計で決め、現段階で新しいschemaやmigrationコードは作らない。

未知のプロトコルや必須機能に出会った旧アプリは、未対応の変更を無視して上書きしない。同期を停止して更新を案内し、既存ローカルデータを保護する。新旧OS版が混在した受入試験を必須にする。将来のDB変更にはmigration、移行前スナップショット、代表fixture、旧版の書き込み拒否、復帰手順を揃える。

初回同期は双方の既存データを合流し、削除を推測しない。再インストールやバックアップ復元は、新しい端末として履歴と再照合する。古いバックアップを共有側の最新状態として無条件に流さず、復元前に同期を止め、復元データを残したうえで差分を確認する。

認証・端末の失効・通信の暗号化・保存先のアクセス制御・保存時の暗号化を必須とする。他の利用者のIDを指定して原本を取得できないことを検証する。ログには画像本文、秘密値、個人のパスを出さない。端末内の資格情報にはOSの保護領域を使う。

サービス運営者にも内容を見せない端末間暗号化は推奨候補。鍵を失った際の復旧、iPhone追加、失効後のアクセス、暗号化後の重複排除、バックアップをセットで設計する。費用や利便性を含む選択なので、実装着手前に採用範囲を決める。ライブラリ原本のハッシュを公開URLや他の利用者の検索キーとして露出させない。

## 8. iPhoneを追加するときの要件

将来のiPhoneアプリは同じライブラリとプロトコルへ参加し、写真/ファイルの追加、一覧・検索・プレビュー、分類、お気に入り、ごみ箱・復元を扱う。共有シートからの取り込み、複数選択、オフライン保存、Wi-Fiのみの原本転送、通信量と空き容量の表示を優先する。撮影素材に含まれる位置情報などは、原本保持の方針と送信対象を説明してから扱う。

iOSのバックグラウンド実行にはOSの制約がある。バックグラウンド転送と再起動時の再接続を利用し、前面復帰時に未反映分を確認する。強制終了や省電力・通信制限中も常時即時同期すると約束せず、待機理由と再開操作を示す。受入試験はシミュレータだけでなく実機で行う。[Appleのバックグラウンド処理の選び方](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)、[バックグラウンドファイル転送](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)

原本を取得していない状態でも一覧から消さず、プレビューや外部アプリへ渡す前に取得を完了する。ダウンロードした作業コピーと管理原本を区別する。iPhoneのローカルキャッシュ解放は、全端末の素材削除として送らない。Windows/Macが停止していても、クラウドへ保存済みの素材を取得できることを推奨構成の受入条件とする。

下記の性能値は設計目標案で、実測値ではない。計測時は端末・OS・ファイル数・総容量・回線条件・キャッシュ状態を記録する。

| --- | --- |
| 小さい変更 | 両PCとサービスがオンライン、RTT100ms以下、実効20Mbps以上、キュー空の条件で、名前・タグ等100変更の相手側反映P95が5秒以内 |
| スクショ | 同条件で5MiB以下の100枚について、保存確定から相手の原本検証・一覧反映までP95が10秒以内 |

| 大容量転送中 | UIで選択・検索・撮影を継続できる。UI更新のP95増加20%以内を既存ローカル版と比較する目標とし、固まり・データ欠損は0件 |
| オフライン・異常終了 | 転送前/途中/検証後/DB適用前後で強制終了。再起動と再接続で最終内容が一致し、二重登録・欠損・誤削除が0件 |

| 時刻差 | 時計が±24時間ずれても変更を失わず、競合結果が到着順に依存しない |
| 故障・制限 | ディスク満杯、途中破損、権限拒否、認証失効、容量上限、429/5xx、長時間切断でデータを守り、復旧後に再開する |

試験の完了は、全対象の原本ハッシュと正規化したメタデータ・分類・検索条件・ごみ箱状態が一致し、未送信/未適用/競合/失敗が意図した件数であることを読み戻して判定する。受信側のアプリ画面も確認する。件数だけ一致しても合格にしない。個人の本番ライブラリを壊す実験はせず、生成したfixtureと隔離ライブラリで検証する。

## 10. 段階と未決定事項

1. Macローカル版: Windows 0.2.10との機能対応表、実装、Mac実機受入。同期要件を理由にこの作業を止めない。
2. 同期設計: 本書の選択事項を確定し、共通プロトコルと競合fixture、移行/復帰、容量別費用、暗号化と鍵の復旧をレビューする。
