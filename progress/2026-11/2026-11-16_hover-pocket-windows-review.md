# Windows 0.2.16 のレビューと指摘の修正

実施日: 2026-11-16 JST。ユーザーの指示「レビューは別のClaudeにやらせて」により、別のClaude（サブエージェント、読み取り専用）が、公開済みの0.2.16（`43687f9..82947e8` の `windows/`）をレビューした。共通ルールの「別の会社のAIによるレビュー」には当たらないが、ユーザーの指示を優先した。修正はClaude（Opus 5.5）が行い、未コミット・未配信。

## レビューの結果

総評は「モニターごとの直列化の骨格は妥当。デッドロック、解放後の使用、P/Invokeの誤りは見つからない。識別子の形式変更で困る呼び出し側もない」。重大1件、要修正4件、提案6件、記述の誤り5件。Claudeが主な指摘をコードで照合し、成り立つことを確認した。

## 直したもの

1. **重大: 検出に一度失敗したモニターが非対応のまま戻らない。** 省電力中や復帰直後に検出し、応答しなかったモニターは、表示構成が変わるかアプリを再起動するまで、スライダーのない「非対応」のままだった。修正前のコードは2分ごとの再検出で回復していた。非対応の行があるときは、30秒たった次の読み取りで再検出する（`BrightnessTiming.UnavailableRetry`）。定期の読み取りで値が取れなかったときは、その場で接続し直す。
2. **要修正: 起動時にショートカットが重なると、撮影設定の保存と画面収録の開始が失敗する（0.2.16で生じた）。** 起動時に重なったキーを含む一覧を保持し、保存時にそれを再登録して「他のアプリが使用中」になっていた。起動時は、登録できたキーだけを保持する。
3. **要修正: 再検出と書き込みが重なると、古い値が表示に戻る。** 再検出の差し替え時に、各モニターの順番待ちを取ったうえで、より新しい値（書き込みで更新されたもの）を新しい窓口へ引き継ぐ。
4. **要修正: 自動起動の修復が、インストールのない開発用PCで開発用フォルダーを毎回登録する。** インストールがあるときだけ修復する。
5. **要修正: 時間切れのテストが、古い結果の上書き防止を外しても通る。** 公開された状態を記録し、古い30%が一度も公開されないことを確かめる形にした。
6. 提案から採用: 再検出の開始前に「構成変化あり」の印を消す（途中に届いた通知を失わない）。診断ログの型番を英数字16文字以内に限る。WMIに載らないモニターの製品名を毎回問い合わせない。UI検査の「Controlsの内容外」判定は常に成り立つ式だったため、横方向のはみ出しと、Controls全体がスクロールできることの検査に替えた。

採用しなかった提案: 先着順でない順番待ちで古い書き込みが後に実行される可能性（パネル側は1台ずつ順に送るため、AI操作と同時の場合に限られる）。未知の識別子への書き込みで毎回全体を開き直す点（頻度が低い）。テストの抜け（自動起動の登録先と実際のRunの値の比較）。

## 記述の誤りの訂正

- 「起動時に1つでもキーが重なると、全部のショートカットが無効になる」は誤り。撮影・収録のキーは先に登録されるため残り、無効になっていたのはそれ以外の追加ショートカット（パネル、設定、ライブラリ、チャットなど）。11月16日の点検記録とコードのコメントを直した。
- 「インストール版の通常起動時に修復する」は、0.2.16では誤りだった（開発版でも動いた）。今回の修正で記述どおりになった。
- 「別のモニターの検出を待たない」が成り立つのは、一覧にある識別子への書き込みの場合。未知の識別子では、進行中の再検出を待つ。
- 偽DDC層のテストは4件ではなく5件だった（今回さらに2件を追加して7件）。

## 検証

- Debug / Release のビルドは警告0・エラー0。`node --check controls.js` も成功。
- `--verify controls`、`settings`、`display`、`capabilities` はexit 0。ショートカットの `--verify ui`（`HOVERPOCKET_CAPTURE_VERIFY_ONLY`）とUI全体の `--verify ui` もexit 0。
- 新しいテストが不具合を捉えることを確かめた。修正を一時的に外すと、それぞれ失敗した。
  - 再検出なし: 「応答し始めても非対応のまま」。
  - 値の引き継ぎなし: 「書いた20%ではなく54%が公開」。
  - 上書き防止なし: 「古い30%が公開（30,50）」。
  - ショートカットの旧い保持の仕方: 「他のアプリが使用中: Ctrl+Alt+F19」で保存に失敗。
  - どの場合も、戻すと合格した。

## 2回目のレビュー（直した箇所の確認）

- 同じレビュー役に、直した箇所の一覧だけを渡して確認を頼んだ。重大1・要修正1〜4は、すべて「解消」と判定された。
- ただし、要修正2の直し方に新しい問題（要修正）があった。差し替えの間に複数のモニターの順番待ちを同時に持つため、遅いモニターの書き込みを待つ間、別のモニターへの書き込みが最大3秒待たされ、「別のモニターを待たない」設計に反していた。デッドロックや解放漏れはなかった。
- 提案2件: 他の呼び出し側の再検出を再利用する分岐で、構成変化の通知が消える。WMIに載らなかったモニターを二度と問い合わせない。

## 2回目のあとの修正

- 差し替えの順番を「差し替え → 古い窓口に退役の印 → モニターごとに1つずつ順番待ちを取り、新しい値を引き継いで放す」に変えた。同時に持つ順番待ちは常に1つになる。
- 再利用の分岐では構成変化の印を戻す。WMIに載らなかったモニターは、1分たてば問い合わせ直す。
- 確実に再現するテストを足した。差し替えの直前に検証用の処理を差し込む内部の入口（`BeforeRegistrySwapForVerify`、通常は何もしない）を設け、サブへの1.5秒の書き込みが順番待ちを持った状態で差し替えを進める。そのときのメインへの書き込み時間を測る。
  - 直した書き方: 32ms で合格（2回）。
  - 2回目の書き方に一時的に戻すと、1,461ms 待たされて失敗した。
  - 最初に作ったテスト（検出中の読み取りに割り込む方式）は、タイミングが偶然に左右されて問題を捉えられなかったため、作り直した。
- 最終の確認: Debug / Release のビルドは警告0・エラー0。`controls`、`settings`、`display`、`capabilities`、`sticky`、`timer`、`ui-model`、ショートカットのUI検証、UI全体の検証はexit 0。

## 受け入れた制約

- 本当に明るさを操作できないモニターが1台でもあると、パネルを開いている間は30秒ごとに全モニターの再検出が走る（1台あたり約60ms＋失敗にかかる時間）。
- 省電力中のモニターは、読み取りに失敗すると一度「非対応」になり、復帰後30秒以内に戻る。

## 残り

- 0.2.17としての配信と本番への適用は未実施（ユーザーの判断待ち）。
- 実機での、省電力から戻った直後の再検出と、複製表示（1つの画面に複数の物理モニター）での識別子と名前の並び順は未確認。
- 別の会社のAI（Codex）によるレビューは行っていない。
- 2回目の確認で見つかった要修正（差し替え時の待ち）の修正は、ユーザーの「確認して配信」の指示で、同じレビュー役が最終確認した。
  - 判定は「解消」。古い値の問題の再発や、退役・値の引き継ぎ・再接続の間の競合もないとされた。
  - 提案2・3の修正と、検証用の入口（製品では何もしない）も問題なしとされた。
  - 結論は「0.2.17は出してよい。重大・要修正は残っていない」。根拠はコードを読んだ範囲で、ビルドと検証はレビュー役は実行していない（Claudeの手元では合格済み）。
  - 後回しにしてよい点として、30秒ごとの全モニター再検出、Reopenの失敗時にも構成変化の印を立てる点、AI操作とパネルの同時書き込みの順番が挙げられた。
