# Windowsのディスプレイ明るさ欄と、サブモニターの明るさ変更の修正

実施日: 2026-11-15 JST。実装: Claude（Opus 5.5）。ブランチ `claude/windows-brightness-20261115`（未コミット）。

ユーザーの依頼は、Controlsのディスプレイ欄で2台目のスライダーが隠れて見えない点と、サブモニターの明るさ変更が効かないことがある点の修正。Codexの週間枠が94%、Claudeの週間枠が81%だったため、ユーザーの選択でClaudeがこの会話で実装した。Codexによる相互レビューは未実施（依頼文は `.ai-peer/tmp/brightness-20261115/review-request.md`、Codexの枠のリセット後に送る）。

## 調査で分かったこと

- この端末のモニター: メインは LG（EDID名「LG ULTRAGEAR+」、GSM7861、主モニター）、サブは HSJ1600（EDID名「U16ZT」、縦置き）。Windowsの説明文はどちらも「Generic PnP Monitor」で、画面では区別できなかった。
- 表示: `controls.css` の `.hp-controls-list { max-height: 82px; overflow-y: auto }` が、2台目の行を一覧の内側に隠していた。
- `GetMonitorCapabilities` は、メインが約1.9秒で成功し、サブは約1.5秒かかって `0xC02625DC`（ERROR_GRAPHICS_MCA_UNSUPPORTED_MCCS_VERSION）で失敗する。VCP 0x10 の読み取りは両方とも約63msで、12回中12回成功した。サブへの書き込みは毎回成功し、約125〜140ms後に読み戻せた。
- 修正前のコードは、2分ごとに全モニターを検出し直していた。その際に能力の問い合わせを含めて、全体のロックを約3.5秒持っていた。その間の書き込みは2.5秒で「失敗」扱いになり、裏で遅れて反映した。識別子は HMONITOR の値から作られ、構成の変化のあとは古い識別子での書き込みが失敗していた。明るさの失敗は診断ログに残らなかった。
- 実際に「効かなかった」場面の記録はないため、上記は原因の有力な候補として扱う。

## 変更

- `DdcPlatform.cs`（新規）: DDC/CIとモニター列挙の呼び出しを差し替え可能な層に分けた。識別子は、EnumDisplayDevices のデバイスインターフェイス名（例: `DISPLAY#HSJ1600#4&124f0533&0&UID69`）から作る。表示名は WmiMonitorID のEDID製品名を使う。
- `MonitorBrightnessService.cs`（書き直し）: 能力の問い合わせをやめ、VCP 0x10 を先に使う（高レベルAPIは予備）。命令はモニターごとに直列化し、別のモニターを待たない。2分ごとの再検出をやめ、構成の変化（DisplaySettingsChanged、復帰）、失敗、未知の識別子のときだけ検出し直す。失敗時は、そのモニターだけ接続し直して1回再試行する。読み戻しは、合わないときに約150ms間隔で最大2回読み直す。時間切れのあとも命令はモニターの順番待ちを保持し、遅れた結果は最新の書き込みのときだけ反映する。失敗は `brightness.write.failed`（理由と型番だけ）として診断ログへ記録する。
- `ControlsModels.cs`: `DisplayBrightnessState` に `IsPrimary` を追加（既存の項目は変更なし）。
- `AppDiagnostics.cs`: 短い理由コード用の `detail` を追加。
- `controls.css` / `controls.js`: 一覧の高さの上限を外し、全行を表示する（パネルが低いときはControls全体がスクロールする）。同じ名前が並ぶときだけ「メイン」「サブ」を添え、名前にツールチップを付けた。
- 検証: `ControlsVerifier.Brightness.cs`（新規）に偽DDC層のテスト（遅いモニターによる待ち、HMONITORの変化、140msの読み戻しの遅れ、時間切れ後の重なりと古い結果の上書き、並び順と名前）を追加した。`--verify ui` には偽の2台・3台×4つの容器サイズでディスプレイ行が切れないかの検査を追加した。素材ライブラリの検査が時間切れになっても、残りの検査を続けるようにした（失敗は記録したまま）。実機の書き込み試験の対象を `HOVERPOCKET_BRIGHTNESS_VERIFY_TARGET` で絞れるようにした。
- `windows/README.md`: 明るさの動作と検証方法を追記した。

## 検証

- Debug / Release のビルドは警告0・エラー0（Shellプロジェクトとソリューション全体）。Release DLLに新しいコードが入っていることを確認した。
- `--verify controls`: exit 0。偽DDCで、片方が遅い状況でのもう片方への書き込みは32ms。実機の読み取りでは2台が「LG ULTRAGEAR+」「U16ZT」と固定IDで認識された。
- `--verify controls --change-brightness`（Release、対象 HSJ1600）: exit 0。73→65→57% の書き込み2回が計533msで読み戻しまで成功し、73%へ戻したことも確認した。別のスクリプトで読み直すと、サブ73%・メイン54%で元どおりだった。
- `--verify capabilities`: exit 0。
- `--verify ui`: exit 0（4回目）。新しいディスプレイ行の検査は、ビルド出力のCSSを一時的に旧版へ戻すと失敗し（「一覧の中でスクロール」「2台目のスライダーが切れる」）、戻した後は通った。
- `node --check`: `controls.js`、`app.js` とも成功。
- 実画面のキャプチャ（`--verify ui` が保存したもの）で、小・大サイズとも「LG ULTRAGEAR+ 54%」「U16ZT 73%」の2行がスライダーまで見えることを目で確認した。小サイズでは「再生中」欄が下へ押し出され、Controls全体のスクロールで見る。
- 見直しで、書き込み中にモニターが外れて登録から消えた場合に解放済みのハンドルを使う経路を見つけ、「変更できませんでした」を返すように直した。直したあと、Debug・Releaseのビルドと `--verify controls` を再実行してexit 0。
- 素材ライブラリのUI検査（お気に入りの星などの実クリック）は、修正前のコード（`43687f9` を一時フォルダーでビルド）でも同じく時間切れになり、修正後も通る回と止まる回がある。今回の修正とは無関係の不安定さとして残す。
