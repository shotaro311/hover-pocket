# Windows版の点検と、見つかった不具合の修正

実施日: 2026-11-16 JST。実装: Claude（Opus 5.5）。ブランチ `claude/windows-brightness-20261115`（未コミット、前日の明るさ修正と同じブランチ）。

ユーザーの依頼は「Windows版で他の問題や改善したほうがいい点があれば、修正しておいてほしい」。Windowsのイベントログ、アプリの診断ログ（`%APPDATA%\HoverPocket\diagnostics`）、自動起動の登録、既存の全検証から問題を探し、根拠のあるものを直した。配信と、インストール済みアプリの置き換えは行っていない。

## 見つけた問題と根拠

1. **サイズ変更のつまみでアプリが落ちる。** 診断ログに、2026-10-06の開発版で `OnUserResize` から `System.Windows.Size..ctor` の `ArgumentException` が未処理例外となって終了した記録がある。今のコードも、つまみを左上へ大きく速く引くと、制限をかける前に負の幅で `Size` を作る。
2. **幅の狭いモニターでパネルを開くと落ちうる。** パネル幅が作業領域と同じになると、左端を決める `Math.Clamp` の上限が丸め誤差で下限を下回り、例外になる。DPI 96〜192と典型的な位置・幅の150通りのうち、13通りで起きることを計算で確認した（例: DPI 120、左端3413、幅864）。保存したパネル幅より作業領域が狭いモニター、たとえば縦置きの1080px幅を125%で使う場合に当たる。
3. **Windowsと一緒に起動しない。** 設定は `startWithWindows=true`。一方、HKCUのRunの `HoverPocket` は、存在しない開発版 `...\bin\Debug\net10.0-windows\HoverPocket.Shell.exe` を指していた。10月11日・15日・22日・11月4日の再起動のいずれでも、アプリの起動記録がない。登録は、設定を変えたときに動いていたexeの場所で書かれ、インストール版がそれを直す仕組みもなかった（9月28日にも同じ問題を手で直した記録がある）。
4. **起動時に1つでもキーが重なると、撮影・収録以外の追加ショートカット（パネル、設定、ライブラリ、チャットなど）がすべて無効になる。** 起動時に元に戻す先は、先に登録した撮影・収録のキーだけのため。（当初「全部が無効」と書いたのは誤りで、レビューで訂正した。この修正には、撮影設定の保存が失敗する不具合があり、[レビューの記録](2026-11-16_hover-pocket-windows-review.md)で直した。）2026-10-06に、開発版とインストール版が同時に動いたときに `shortcuts.registration.failed` が記録されている。

あわせて、検証の不安定さを1つ直した。素材ライブラリのUI検査は、ホバーで現れるお気に入りの星を、ホバーが反映される前にクリックしていた。修正前のコードでも毎回違う行で時間切れになっていた。

## 修正

- `HoverShellController.Ux.cs`: 幅と高さを0以上にし、有限の値のときだけ `Size` を作る。
- `HoverShellController.cs`: `ClampLeft` を追加し、上限が下限を下回らないようにした（2か所）。
- `RunKeyStartupRegistrationService.cs`: 登録先を、Velopackが作るスタートメニューのショートカットと同じ `%LOCALAPPDATA%\HoverPocketWin\current\HoverPocket.Shell.exe` にした（更新しても場所は変わらない）。インストールがあれば、開発版からの操作でもそちらを登録する。
- `PanelBridgeController.cs` / `App.xaml.cs`: 通常起動の時に、設定がオンで登録が違えば登録し直す `RepairStartupRegistration` を追加した。直した場合は `startup.registration.repaired` を記録する。検証用の起動では動かない。
- `CaptureHotkeys.cs` / `CaptureController.cs` / `App.xaml.cs`: 起動時は、登録できたショートカットを有効にし、重なった数だけを `shortcuts.registration.partial` として記録する。設定画面からの変更は従来どおり、全部成功しなければ元に戻す。
- 検証: `PanelResizeVerifier` に画面外へ引くケース、`DisplayVerifier` に150通りの左端計算、`SettingsVerifier` に自動起動の修復4通り、`CaptureVerifier` に起動時の部分登録を足した。`AssetInteractionVerifier` は、カーソルの下が目的の部品になるまで最大1.5秒待ってからクリックする。

## 検証

- Debug / Release のソリューション全体のビルドは警告0・エラー0。
- `--verify` を18種類、1つずつ実行した。`shell`（100回開閉を含む）、`display`（追加した150通りの左端計算を含む）、`ui-model`、`sticky`、`clipboard`、`calc`、`timer`、`weather`、`calendar`、`settings`（追加した自動起動の修復4通りを含む）、`ailane`、`pocket-surface`、`broker`、`voice`、`updater`、`controls`、`capabilities` はexit 0。`release-config` は、Release構成と公開用のGoogle OAuth設定・版番号を前提にする検査で、Debugでは仕様どおりexit 1（今回の変更と無関係）。
- `--verify ui` の個別検証: ショートカット（`HOVERPOCKET_CAPTURE_VERIFY_ONLY`、起動時の部分登録を含む）とサイズ変更（`HOVERPOCKET_RESIZE_VERIFY_ONLY`、画面外へ引くケースを含む84ケース。各サイズでControlsのカード内の部品の切れもなし）はexit 0。
- サイズ変更の修正を一時的に修正前の1行へ戻すと、同じ検証が `ArgumentException: 幅と高さは正の値でなければなりません。` で失敗した。戻したあとは合格し、コードを元に戻して再ビルドした。
- `--verify ui` 全体を2回続けて実行した。1回目はexit 0。2回目は、星のクリックは通ったが、インライン編集中のヘッダーの再読み込みボタンへの実クリックが届かずexit 1（カーソルの下にボタンはあるのにクリック0回）。検証中も動いているインストール版0.2.15が、上端へのカーソル移動に反応して重なり、クリックを受け取っている可能性がある（未確認。インストール版を止めて検証すれば確かめられる）。

- 最後に登録先の変更とコメントの整理をしたあと、Debug・Releaseのビルドと `settings`・`display`・`controls`・`capabilities` を再実行して合格した。
- 素材の星のクリックの待ち合わせは、修正後の全体実行2回で2回とも通った。2回だけなので、安定したと断定はしない。

## インストール版への影響の確認

検証の実行中も、インストール版0.2.15（PID 21864）は動いたままだった。読み取りだけで確認した。

- PID 21864 は応答中。明るさはメイン54%・サブ73%で、元のまま。HKCUのRunの値は変わっていない。
- 実データで今夜変わったのは、23:17の画像1件（クリップボードと素材ライブラリへの自動保存）、23:18の付箋・天気・設定、23:33〜0:06のクリップボードのテキスト6件。時刻はいずれも検証を始める前か、ユーザーが操作していた時間帯だった。テキストはリポジトリ内の検証用データと一致せず、うち2件はこのプロジェクトの用語を含むため、ユーザー自身のコピーと判断した（本文は表示していない）。

## 触っていないもの・未確認

- Windowsの「設定 → アプリ → スタートアップ」の状態（StartupApproved）には触れていない。HoverPocketには2026-08-05付けで先頭が `01` の印がある。公式の仕様はないが、Mozillaの実装コメントでは先頭が奇数なら無効とされ、同じ印のGpuPeekとDocker Desktopも起動していないため、Windows側でオフの可能性が高い。今回の修正だけでは、自動起動しない可能性がある。
- 今のHKCUのRunの値は書き換えていない。修正版をインストールして起動すると直る。実際の再起動での自動起動は未確認。
- 幅の狭いモニターでの例外は計算と合成データでの確認だけで、実機では再現していない（この端末のサブは1097DIPと十分広い）。
